## 2026-08-04 — 화면/라우트 단위 접근 제한은 scope 이름을 해시 경로 그대로 `/` 접두해 정한다, 템플릿에 RouteGate 기본 탑재

**맥락**: mockingbird-showcase 에서 관리 화면으로 `/#/ask` 에 접근 제한을 걸었는데도 실제
화면은 그대로 열렸다. 원인은 AuthGate 의 `useProjectPermission()` 이 scope 없이(앱 전체
기본 scope 만) 호출되고, 화면별로 scope 를 지정해 판정하는 코드가 어디에도 없었기 때문 —
이 platform 은 "관리 화면에서 scope 등록"과 "코드에서 그 scope 조회"가 별개 단계라, 후자가
없으면 전자는 아무 효과가 없다. 이 문제는 bbq-telestration 템플릿 자체에도 잠재해 있었다(애초에
`lib/permission/*` 가 없어 화면 단위는커녕 앱 단위 서버 등록 게이트조차 못 걸었음).

**결정**:
1. 화면/라우트 단위 게이트 컴포넌트 `lib/permission/RouteGate.tsx` 를 도입하고, scope 이름
   규칙을 **해시 경로 그대로 `/` 를 접두한 문자열**로 고정한다(`#/ask` → scope `/ask`).
   관리 화면에서 이 표기와 정확히 일치하게 등록해야 적용된다.
2. 이 bbq-telestration 템플릿에 `lib/permission/*` 전체(자체 멤버십 기반 동적/정적 판정 세트) +
   `RouteGate.tsx` 를 기본 탑재해, 앞으로 scaffold 되는 모든 새 App 이 처음부터 이 권한
   시스템을 상속받게 한다(화면이 여러 개로 늘어나도 바로 RouteGate 를 꺼내 쓸 수 있음).

**대안**:
- 화면마다 매번 `useProjectPermission(scope)` 를 직접 호출하고 로딩/차단 렌더를 개별 작성 —
  기각. 매번 다시 배선해야 해 이번 mockingbird-showcase 사례처럼 빠뜨리기 쉽다.
- scope 이름을 라우트 이름과 무관하게 자유 문자열로 둔다 — 기각. 등록 시점과 조회 시점의
  문자열이 프로젝트마다 다른 관례로 어긋나기 쉬워, 정확히 일치해야 하는 fail-open 시스템에서
  조용히 무력화되는 사고가 반복될 위험이 있다.
- 플랫폼(서버) 차원에서 라우트→scope 자동 매핑을 만든다 — 보류. 해시 라우팅은 서버에서
  보이지 않아 근본적으로 클라이언트 코드가 판단해야 하고, 지금은 이 정도 컨벤션 고정으로
  충분하다고 판단.

**근거**: 해시 경로를 그대로 쓰면 관리 화면에서 등록할 때 "이 화면이 어떤 scope 인지"를
따로 기억하거나 문서를 찾아볼 필요가 없다 — URL 을 보고 그대로 입력하면 된다. 템플릿에
기본 탑재하면 이 컨벤션 자체가 별도 안내 없이 전파된다.

**영향**: 화면을 새로 추가하는 프로젝트는 `App.tsx` 라우트 분기에서 `<RouteGate scope="/새화면">`
로 감싸기만 하면 되고, 관리 화면에서 그 scope 를 정확히 그 문자열로 등록해야 실제 적용된다
(다르면 미등록으로 간주돼 fail-open). 기존에 이미 scaffold 된 App 들은 자동으로 상속받지
못하므로 개별 백포트가 필요하다.
